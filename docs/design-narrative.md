# Design narrative — encrypted polygenic risk scoring

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna). — v0.13.0_

This is the "why" behind the application: what we decided at each step, what we
ruled out, and how we know the design is sound. It is written for a reader new
to Fully Homomorphic Encryption (FHE) — the technique that lets an outside
computer do arithmetic on data it cannot read.

## The problem

> _We run a genomics research biobank. We want to score inherited disease risk
> from each participant's genetic profile — a few thousand genetic markers per
> person — and we'd offload the actual scoring to an outside compute provider.
> However, that genotype is the most sensitive data we hold. Can we set it up so
> the scoring happens without whoever runs it ever seeing the actual genotype?_

A **polygenic risk score (PRS)** turns a person's genetic markers into a single
number estimating their inherited risk for a disease. Mechanically it is a
**weighted sum**: for each marker you take the person's *dosage* (how many copies
of the risk variant they carry — 0, 1, or 2) and multiply it by that marker's
published *effect weight* (how strongly that variant is associated with the
disease), then add the products across all the markers.

    score(person) = sum over markers of  dosage(marker) x weight(marker)

The dosages are the sensitive data. The goal is to let an outside provider
compute that sum for a whole study cohort without ever seeing a single dosage.

## The decisions, stage by stage

### Implementation path and audience
Built with the **Niobium DSL** (a higher-level language that generates the
OpenFHE program), at the request of a user new to FHE and new to PRS. All FHE
and genetics terms are introduced in plain language here and in the README.

### Stage 1 — Privacy model
- **Parties.** The **biobank** (holds the genotypes, encrypts them, holds the
  one key that can decrypt); the **compute provider** (runs the scoring, never
  gets the key, so it computes *blind*). The adversary of interest is an
  honest-but-curious provider — it does the job correctly but might try to learn
  genotypes from what it handles.
- **Who encrypts.** One party — the biobank — encrypts the entire cohort. This
  "single encryptor" setting is what lets us pack many participants together and
  score them in one pass (Stage 5).
- **Who decrypts / who acts.** The biobank does both. Because the party that
  decrypts is also the party that uses the scores, there is no need for the
  extra machinery (transciphering) that a hand-off to a third party would
  require.
- **The weights are public.** They come from published genome-wide association
  studies (the PGS Catalog and similar). Public numbers do not need to be
  encrypted, so the provider multiplies the encrypted dosages by plain weights —
  which is what keeps the computation as cheap as it is.
- **What crosses the boundary.** Client-side (in the clear, at the biobank):
  load dosages, impute/clip, encrypt, and later decrypt. Server-side (encrypted,
  at the provider): the weighted sum. Nothing sensitive is ever in the clear on
  the provider.

An honest note we put on the record: because the weights are public *and* the
biobank holds the genotypes, the biobank could in principle compute these scores
in-house. What FHE buys here is not an otherwise-impossible computation — it is
the ability to **safely offload** the work (to scale, to managed infrastructure,
to many PRS models) without the outside party ever seeing a genotype.

### Stage 2 — Feasibility
Green on every axis, and unusually so:
- **No branching on the data.** The score is the same multiply-and-add for
  everyone, whatever their genotype — exactly what FHE needs.
- **One lane, pure arithmetic.** Only multiply and add; no comparisons, no
  curves to approximate. This avoids the most expensive FHE machinery entirely.
- **Depth ≈ 1.** "Depth" — the length of the longest chain of multiplications
  stacked on each other — is the resource that drives FHE cost. A PRS needs
  exactly one multiply per marker (dosage × weight) and then additions (which
  are essentially free). One multiplication deep is the shallow, cheap end of
  the scale.
- **Parallelism.** Because one party encrypts the whole cohort, up to 32,768
  participants ride in the slots of a single encrypted object and are scored
  together.

### Stage 3 — The plaintext reference and the data
The reference computation is the standard PRS formula (identical to what tools
like PLINK `--score` produce). Because real genotypes are exactly what we are
protecting, we scored against a **synthetic cohort** generated with the standard
liability-threshold model of statistical genetics: realistic allele frequencies,
genotypes drawn under Hardy-Weinberg, an independently simulated disease
outcome, and published weights that are a *noisy* estimate of the true effects
(as real published weights are). The synthetic PRS reaches **AUC 0.76** against
the simulated disease, and its top-decile carries **3.2×** the base disease rate
— a realistic, genuinely useful risk score, not a tautology (the disease labels
are drawn independently of the score). Swap in real dosages and real weights and
nothing downstream changes.

### Stage 4 — Scheme
**CKKS** — the FHE scheme for real-number arithmetic. A risk score is a real
number used for ranking and thresholding, so approximate real arithmetic with a
faint hiss of noise is exactly right, and CKKS is what the target platform (the
Niobium Fog) runs.

### Stage 5 — The circuit
- **Packing (column-major).** One ciphertext per marker; the 32,768 slots inside
  it hold that marker's dosage for 32,768 different participants. Multiplying
  that ciphertext by the marker's public weight scales all 32,768 participants at
  once; adding the per-marker ciphertexts accumulates each participant's score in
  their own slot. Out comes **one** ciphertext whose slot *p* is participant
  *p*'s score.
- **No rotations, no relinearization on the critical path.** Because scoring is a
  ciphertext-times-plain-number multiply-accumulate, none of the usual
  slot-shuffling or ciphertext-product cleanup is needed.
- **Depth budget:** 1 multiplicative level used.

### Stage 6 — Parameters
CKKS at ring dimension **2^16** (65,536), **128-bit** classical security,
multiplicative **depth 2** (1 used + 1 spare, applying the "budget one more"
pessimism rule), **scaling 45 bits**, **first modulus 60 bits**. We predicted
decode safety from the plaintext side before spending an encrypted run: the
modulus budget offers **105 bits** against a **57-bit** need — a ~48-bit margin.
Ciphertext sizing: ~3.1 MB per marker ciphertext, so ~6 GB uploaded to score a
full cohort (small per participant; a batch job).

### Stage 7 — The faithful twin (the gate)
The twin is a plain-number model of the *exact* circuit (same packing, same
fixed-point rounding, same multiply-accumulate). Against the reference it was
essentially exact — max error **9e-13**, rank correlation **1.000**, **zero**
participants moved in or out of the high-risk decile — and decode-safe with wide
margin. A noise-injection study showed zero high-risk changes up to a per-slot
noise sd of **1e-05**, more than two orders of magnitude above the ~6e-08 the
encrypted run turned out to produce. That was the green light to build the
encrypted version.

### Stage 8 — Implementation (Niobium DSL)
Three short `.niob` files (`shared`, `client`, `server`) generate the four-program
pipeline: `keygen`, `encrypt`, `score` (the only part the provider runs), and
`decrypt`. The trust boundary is enforced two ways: the DSL makes secret-key
access a compile error in server code, and a runtime guard refuses to start the
server if a secret key is present in its home (a reviewer can plant one and watch
the refusal). A two-process demo stands the client and provider up as separate
processes exchanging only ciphertext.

## Dead ends and alternatives considered
- **Row-major packing (one ciphertext per participant).** Would need one
  ciphertext per person plus slot-summing rotations and rotation keys, and would
  emit one near-empty output ciphertext per person. Column-major is strictly
  better here because the marker count (a few thousand) is smaller than the
  participant count and it produces a single dense output. Rejected.
- **Encrypting the weights.** Unnecessary — the weights are public. Encrypting
  them would turn each multiply into a ciphertext×ciphertext product (needing
  relinearization) for no privacy gain. Rejected.
- **Transciphering for output integrity.** Only needed when the party that
  decrypts differs from the party that consumes the result. Here they are the
  same (the biobank), so it would be dead weight. Not used.
- **Bootstrapping / deeper parameters.** Irrelevant at depth 1. Not used.

## Implementation notes (Stage 8 addendum)
- The DSL emits a default set of rotation keys (~220 MiB) even though this circuit
  performs no rotations; the harness copies whatever public/evaluation keys
  `keygen` emits (never the secret key), so this is handled without relying on a
  fixed key list.
- Peak server memory during scoring was **12.23 GiB** for 2,000 markers — the
  working set is dominated by holding all marker ciphertexts at once, so it
  scales with the marker count. A production provider should size RAM
  accordingly (see the results report).

## Final design in one line
CKKS at ring 2^16 / depth 2, column-major packing of a whole cohort, a single
depth-1 weighted sum of encrypted dosages against public weights — reproducing
the plaintext risk score to ~5e-08 with zero high-risk reclassifications, while
the compute provider sees only ciphertext.
