# Protocol and threat model — encrypted polygenic risk scoring

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna). — v0.13.0_

## Parties

| Party | Role | Holds | Sees |
|---|---|---|---|
| **Biobank** (client) | Owns the genotypes, encrypts, decrypts | Genotype dosages, the secret key, the public weights | Everything (it is the data owner) |
| **Compute provider** (server) | Runs the encrypted scoring | The context, public key, evaluation keys, and the **public** weights | Only ciphertext — never a dosage, never a score |

The provider is assumed **honest-but-curious**: it runs the correct computation
but may inspect anything it holds to try to learn genotypes.

## Message flow

The application runs as two processes on two hosts (a client home and a server
home); only the files listed as "→ server" ever leave the biobank.

**Setup (once per key epoch):**

| Step | Direction | Payload | Sensitive? |
|---|---|---|---|
| 1 | biobank → provider | crypto context + public key + evaluation keys | no |
| 2 | biobank → provider | public per-marker weights (`weights.txt`) | no (published) |

**Per scoring job (per cohort batch of ≤ 32,768 participants):**

| Step | Direction | Payload | Sensitive? |
|---|---|---|---|
| 3 | biobank → provider | one encrypted ciphertext per marker (the dosages) | encrypted |
| 4 | provider | runs the weighted-sum circuit on the ciphertexts | — |
| 5 | provider → biobank | one encrypted ciphertext of scores | encrypted |
| 6 | biobank | decrypts with the secret key; reads the scores | — |

**Files that live only on the biobank host:** the secret key, the plaintext
genotype dosages, the decrypted scores.
**Files on the provider host:** the context, public key, evaluation keys, and
the public weights — nothing that can decrypt anything. The server home is safe
to copy to untrusted infrastructure as-is.

## What each party can and cannot learn

- **The provider** sees a fixed number of ciphertexts (equal to the marker
  count) and returns one ciphertext. Under the standard security assumption for
  CKKS (Ring Learning-With-Errors), the ciphertexts are indistinguishable from
  random without the secret key. The provider therefore learns **no dosage and
  no score**. It does learn the *public* facts of the job: how many markers, how
  many participants (batch shape), and that a PRS is being computed with the
  given public weights.
- **The biobank** learns the scores — which is the point. It already owns the
  genotypes, so nothing is revealed to it that it did not already hold.

## Intentional output (the protocol result)
The decrypted per-participant risk scores. These go only to the biobank.

## Incidental leakage (accepted)
- **Cohort/marker counts.** The number of ciphertexts reveals the marker count;
  the batch count reveals the cohort size to within a 32,768 rounding. These are
  operational metadata, not genotypes.
- **Timing.** Server runtime scales with the marker count, not with any dosage
  value, so timing does not leak genotypes.
- No per-record rejection occurs (see below), so nothing is leaked through a
  reject channel.

## Input screening / bounds enforcement
The client imputes missing calls (to the marker's mean dosage) and clips every
dosage into `[0, 2]` before encrypting, using the committed `marker_bounds.csv`.
For this **linear** circuit this is genotype data hygiene, **not** a
decode-safety filter: a weighted sum has no polynomial that could diverge on an
out-of-range value, so no participant is ever rejected and batched packing is
safe by construction. Reject rate: **0%**. There is consequently no reject-set
composition to report.

## Output integrity
Not applicable in this engagement: the party that decrypts (the biobank) is the
party that consumes the scores. There is no second party who must be assured the
score was not altered, so no transciphering or signature layer is needed. If a
future deployment hands scores to a third party who must trust them, revisit
this with a transciphering (dual-output) design.

## Threats NOT addressed
- **A malicious (not merely curious) provider** that returns a wrong or
  adversarially-crafted ciphertext. FHE guarantees the *computation* is correct
  if performed as specified; it does not force the provider to perform it. Verify
  correctness out of band if the provider is untrusted for integrity (e.g. spot
  re-scoring, or a transciphering/attestation layer).
- **Client-side compromise.** If the biobank host is breached, the secret key
  and plaintext genotypes are exposed — FHE protects data *in the provider's
  hands*, not on the owner's own machine.
- **Model inversion via the output.** FHE protects inputs, not outputs. A risk
  score is a lossy aggregate of thousands of markers, so a single score reveals
  little about any one marker; but repeated scoring of the same person under
  many different published weight sets could, in principle, constrain their
  genotype. Because the biobank is the only party that ever sees scores, this is
  an internal governance matter, not an exposure to the provider.
- **Side channels** (memory-access patterns, power) on the provider host.
- **Denial of service** and **collusion** among multiple providers.
