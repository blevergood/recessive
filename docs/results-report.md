# Results report — encrypted polygenic risk scoring

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna). — v0.13.0_

## How we know it passes (in plain language)

**(a) The answer key.** We first computed every participant's polygenic risk
score the ordinary way, in the clear, with a standard scorer (the same weighted
sum PLINK `--score` performs). Those plaintext scores — produced with no
encryption involved — are the answer key.

**(b) The test.** We then encrypted the same participants' genetic markers, sent
them to a compute process that ran the scoring **blind** (it held no decryption
key and logged only byte counts), got back an encrypted result, decrypted it,
and laid those scores side by side with the answer key. The decrypted scores
matched to a **maximum difference of about 0.00000006** (6e-08) across all 8,000
participants — and **not one participant** moved into or out of the
"high genetic risk" top decile. The ranking was identical (rank correlation
1.000).

**(c) Why there is any difference at all.** Two small, expected sources. First,
encryption works on a fixed-point grid rather than exact decimals — that
contributes error around 1e-13, far too small to matter. Second, CKKS
encryption adds a faint numerical hiss; here it is around 1e-08. Both were
budgeted for in advance, and both are ~100,000× smaller than the amount of noise
it would take to change even a single high-risk decision.

**(d) Why it isn't a lucky run.** The same agreement showed up at every
independent check: the faithful twin vs the reference (Stage 7, before any
encryption), the local plain-OpenFHE run (`--cpu`), the trace-simulator run that
rehearses the deployment path (`--sim`), and the two-process client/server demo.
Four different layers, the same near-perfect agreement.

**(e) The honest caveat.** "Matches the reference" means the encrypted pipeline
faithfully reproduces the *scoring computation* — it does **not** claim the score
is a perfect predictor of disease. How well a PRS predicts disease is a property
of the weights and the biology (here, on synthetic data, AUC 0.76); the FHE work
neither improves nor harms it. What we guarantee is that offloading the scoring
to an outside provider costs you essentially nothing in accuracy and reveals
nothing to that provider.

## Parameters

| Parameter | Value | Note |
|---|---|---|
| Scheme | CKKS | approximate real arithmetic |
| Ring dimension N | 65,536 (2^16) | 32,768 slots = participants per batch |
| Security | 128-bit classical | logQ ≈ 150 ≪ the 2^16 budget — wide margin |
| Multiplicative depth | 2 | 1 used + 1 spare (pessimism rule) |
| Scaling modulus | 45 bits | precision per level |
| First modulus | 60 bits | initial headroom |
| Markers (N_MARKERS) | 2,000 | representative "few thousand"; scales linearly |
| Participants | 8,000 | one 32,768-slot batch |
| Rotations / relin on critical path | none | pure ct × public-scalar multiply-accumulate |

## Boundary sizes and server footprint (measured, `--cpu`)

| Boundary | Size | |
|---|---|---|
| Context (`cc.bin`) | ~0.03 MiB | sent once |
| Public key (`pk.bin`) | 3.0 MiB | sent once |
| Eval-mult key (`mk.bin`) | 10.0 MiB | sent once |
| Rotation keys (`rk.bin`) | 220.0 MiB | sent once; unused by this circuit |
| **Upload / job** (marker ciphertexts) | **6,002 MiB (~6 GB)** | ~3.1 MiB × 2,000 markers |
| **Download / job** (score ciphertext) | **3.0 MiB** | one ciphertext for the whole cohort |

| Mode | Participants | Peak server memory |
|---|---|---|
| `--cpu` | 8,000 (one 32,768-slot batch) | **12.23 GiB** |

**Sizing guidance for a real deployment.** Server memory is dominated by holding
all marker ciphertexts at once, so it scales with the marker count: budget
roughly **6 MiB of peak RSS per marker** (≈ 12 GiB at 2,000 markers). Upload
scales the same way (~3 MiB per marker per batch). The result download is a
single ciphertext regardless of cohort size, and per-participant cost is tiny
because one batch scores up to 32,768 people. To score a cohort larger than
32,768, the identical circuit repeats over additional 32,768-participant batches.

## Noise tolerance (recorded at the Stage 7 gate)

Injecting synthetic per-participant noise into the twin: **zero** high-risk
reclassifications up to a noise standard deviation of **1e-05**; the first flips
(2 of 8,000, at the exact decile boundary) appear only at **1e-04**. CKKS
delivers ~1e-08 here — comfortably inside the zero-flip region.

## Fog deployment (Stage 10)

The same binary that passed `--cpu` was validated on the Fog execution path by
simulation (`--sim`): the session records the computation as a trace and the
local simulator reconstructs the result, which matched the twin to **5.38e-08**
with zero high-risk flips. Dispatching to live Fog hardware (the default
`./run_test.sh`) additionally requires a Fog API key (`fog login`); the design,
circuit, and expected results are identical — only where the scoring runs
changes.

## Bottom line

**PASS.** The encrypted pipeline reproduces the plaintext polygenic risk scores
to ~5e-08 with zero changes to who is flagged high genetic risk, while the
compute provider handles only ciphertext and never sees a genotype or a score.
On synthetic data the score itself is a realistic, useful risk stratifier
(AUC 0.76, 3.2× top-decile enrichment); swapping in real dosages and real
published weights changes none of the FHE machinery.
