# Recessive

_Generated by the Niobium FHE Application Design AI Assistant (FHEanna). — v0.13.0_

> Every marker is carried into the score. Not one is ever expressed.

Inherited disease risk, scored for a whole study cohort on an outside compute
provider that never sees a genotype. The biobank encrypts each participant's
marker dosages, the provider computes the scores holding no key that can
decrypt them, and the biobank decrypts the results. Built with Fully
Homomorphic Encryption (FHE), which performs arithmetic directly on ciphertext.

**This is a demonstration of encrypted computation, not a clinical or
diagnostic tool. The cohort in this repository is synthetic.**

## Initial prompt

> _We run a genomics research biobank. We want to score inherited disease risk
> from each participant's genetic profile — a few thousand genetic markers per
> person — and we'd offload the actual scoring to an outside compute provider.
> However, that genotype is the most sensitive data we hold. Can we set it up so
> the scoring happens without whoever runs it ever seeing the actual genotype?
> We'd send the marker values per participant, encrypted, and get back a risk
> score for each. Needs to handle a whole study cohort in one go._

## The computation

A **polygenic risk score (PRS)** condenses thousands of common variants into one
number. At each marker you take the participant's **dosage** (how many copies of
the risk allele they carry: 0, 1 or 2), multiply by that marker's published
**effect weight** from a genome-wide association study, and sum across the panel:

```
score(participant) = sum over markers of  dosage[marker] x weight[marker]
```

Participant 0 of the bundled cohort, over a 2,000-marker panel:

| marker | MAF | dosage | weight | contribution |
|---|---:|---:|---:|---:|
| m0000 | 0.390 | 1 | -0.05436 | -0.05436 |
| m0001 | 0.233 | 0 | -0.06742 | 0 |
| m0002 | 0.303 | 1 | -0.00898 | -0.00898 |
| m0003 | 0.083 | 0 | -0.05276 | 0 |
| ... (1,996 more) | | | | |
| **score** | | | | **-2.73867** |

That number carries no unit; it is read as a rank. -2.73867 puts participant 0
at the 6th percentile of this cohort. The use for a PRS is **stratification**.
Split a cohort by score and the top slice is the group worth screening early or
recruiting into a prevention trial. Splitting the run's 8,000 participants into
deciles, against their ground-truth disease status:

| decile | n | mean score | cases | case rate |
|---:|---:|---:|---:|---:|
| 1 | 800 | -2.954 | 4 | 0.005 |
| 5 | 800 | -1.194 | 68 | 0.085 |
| 10 | 800 | 0.872 | 257 | 0.321 |
| all | 8,000 | -1.050 | 800 | 0.100 |

The top decile carries 3.2× the cohort base rate and the bottom decile a
twentieth of it, for an AUC of 0.7572. Those numbers come from the decrypted
output of an encrypted run, and match the plaintext scorer to the fourth decimal.

## Under encryption

A weighted sum against **public** weights is close to the cheapest circuit FHE
has:

- **One multiplication deep.** Each marker costs one `dosage × weight`; the
  additions after it are nearly free. Depth drives FHE cost, and this is the
  shallow end.
- **Ciphertext × plaintext only.** GWAS effect weights are published (PGS
  Catalog and similar), so they stay in the clear on the provider. No
  ciphertext-ciphertext product means no relinearization.
- **No data-dependent branching**, no comparisons, no functions to approximate.
- **No rotations**, so no rotation keys on the critical path.

**Packing.** CKKS at ring 2^16 carries 32,768 slots per ciphertext. The cohort
is packed *column-major*: one ciphertext per **marker**, holding that marker's
dosage for 32,768 different **participants**. Multiplying it by the marker's
weight scales all 32,768 participants at once, and adding the per-marker
ciphertexts accumulates each participant's score in their own slot. One
ciphertext comes back, with slot *p* holding participant *p*'s score.

So for 2,000 markers and 8,000 participants, the provider's entire job is 2,000
ciphertext × plaintext multiplies and 1,999 additions, at ~12 GiB peak RSS, on
input it cannot read.

## Trust boundary

| | Biobank (client) | Compute provider (server) |
|---|---|---|
| holds | dosages, secret key, scores | context, public + evaluation keys, public weights |
| sees | everything (it owns the data) | ciphertext only |
| runs | keygen, encrypt, decrypt | the weighted sum |

The provider is assumed honest-but-curious. It learns the *shape* of the job
(2,000 markers, one 32,768-slot batch) and nothing about any dosage or score.
The DSL makes secret-key access a compile error in `@server` code, and
[server_guard.sh](server_guard.sh) refuses to launch the server if a secret key
is present in its home; `run_test.sh` plants one and checks for the refusal
before every run. Full detail in
[docs/protocol-threat-model.md](docs/protocol-threat-model.md).

## Evaluation data & features

> **The data in this repository is SYNTHETIC.** Real participant genotypes are
> exactly the sensitive data this application protects, so none ship here. The
> cohort is generated with the standard liability-threshold model of statistical
> genetics (realistic allele frequencies, Hardy-Weinberg genotypes, an
> independently simulated disease outcome, and published weights that are a noisy
> estimate of the true effects). Swap in your real dosage matrix and real
> published weights. Nothing in the FHE design changes. See
> [harness/gen_data.py](harness/gen_data.py).

| Item | Value |
|---|---|
| Participants (cohort) | 8,000 (one 32,768-slot batch) |
| Markers per participant | 2,000 (a representative "few thousand"; scales linearly) |
| Dosage per marker | 0 / 1 / 2 (count of risk alleles) |
| Weights | public per-marker effect sizes |
| Simulated disease | 10% prevalence; PRS reaches AUC 0.76, top-decile 3.2× base rate |
| Scheme | CKKS, ring 2^16, 128-bit classical, depth 2 (1 used), scaling 45 bits |

The disease labels are drawn from an independent latent liability, so the AUC
measures how well the score stratifies risk and cannot be inflated by
construction.

## Quickstart

```bash
# 1. generate the synthetic cohort, the reference, and the faithful twin.
#    REQUIRED on a fresh clone: data/ is generated in full and none of it is
#    committed, and run_test.sh's correctness gate reads the two score CSVs
#    that validate_twin.py writes.
./run-in-container.sh "python3 harness/gen_data.py"
./run-in-container.sh "cd harness && python3 validate_twin.py"   # Stage 7 gate

# 2. pack the inputs (impute + clip + column-major) and export public weights
./run-in-container.sh "python3 harness/prepare_inputs.py"

# 3. build the FHE binaries (compiles the .niob DSL -> OpenFHE C++ -> binaries)
./run-in-container.sh "make build"

# 4. run it: no flag dispatches to the Niobium Fog (the default, needs an API key);
#    --cpu and --sim validate locally with no account
./run-in-container.sh "./run_test.sh"          # the Niobium Fog (default)
./run-in-container.sh "./run_test.sh --cpu"    # local validation (the correctness gate)
```

**About `nb_out/`.** The committed `nb_out/` is the OpenFHE C++ that `nbc` generated
from the `.niob` sources, checked in so you can read the exact FHE circuit the DSL
produces. It is a **snapshot, not pinned to a container version**: `make build`
recompiles the `.niob` sources with your image's `nbc` and overwrites `nb_out/` before
building, so the binaries you run always match your toolchain. If the toolchain has
moved since the snapshot was committed, `git status` will show changes under `nb_out/`
after a build. That is expected, and the `.niob` sources are the source of truth.

## Run modes

`run_test.sh` runs keygen → encrypt → score → decrypt across a **client home**
and a **server home** (the secret key never enters the server home), then reports
the scores, task quality, encryption fidelity, and the deployment profile.

| Command | What it does | Needs |
|---|---|---|
| `./run_test.sh` (no flag) | dispatches the scoring to the **Niobium Fog** (the default) | a Fog API key (`fog login`) |
| `./run_test.sh --cpu` | plain-OpenFHE local run, the correctness gate | Docker |
| `./run_test.sh --sim` | records a trace, replays it in the local simulator (a faithful rehearsal of the Fog run) | Docker |
| `./run_test.sh --sim-full` | as `--sim` plus a bit-exact ring-level identity check | Docker |

Run any of them in the container, e.g. `./run-in-container.sh "./run_test.sh --sim"`.

Streams are split so a redirect keeps the report whole: the score report goes to
stdout, the stage table to stderr, and the OpenFHE/Fog tool output to
`run_<mode>/tools.log`. `-v` passes the tool output through instead, `-q` drops
the stage table, and the exit status is 0 only when the decrypted scores match
the faithful twin inside the Stage 7 tolerance with no high-risk
reclassification.

## Two-process demo (the deployment shape)

Stands the biobank client and the untrusted provider up as **separate processes**
talking only over HTTP, exchanging ciphertext, never keys that decrypt and
never plaintext. It also runs a negative test first: a secret key planted in the server
home makes the server refuse to start (exit 13).

```bash
./run-in-container.sh "python3 harness/demo_two_process.py"
```

## How correctness is established

Three versions of the same computation, each measured against the one before:

1. **Reference** ([refmodel.py](harness/refmodel.py)). The standard PRS formula
   in plain float64, identical to what PLINK `--score` produces. Measured
   against the ground-truth disease phenotype.
2. **Faithful twin** ([twin.py](harness/twin.py)). The *exact* circuit in plain
   numbers: same column-major packing, same fixed-point rounding, same
   multiply-accumulate order. Max deviation from the reference 9e-13, zero
   participants moved across the high-risk decile boundary. This is the Stage 7
   gate; it runs before any encrypted code is built.
3. **Encrypted.** The decrypted FHE output against the twin. Max deviation
   under 1e-07 (5 to 6e-08 across runs), zero high-risk reclassifications.

`validate_twin.py` also runs a noise-injection study before the encrypted build:
zero participants change decile up to a per-slot noise sd of 1e-05, two orders of
magnitude above what an encrypted run produces. The `run_test.sh` gate then checks
two things independently: `max |FHE - twin| <= 1e-2`, and that no participant is
reclassified at all.

CKKS is approximate, so scores come back carrying under 1e-07 of noise. That is
fine for ranking and thresholding; check the tolerance before using a PRS output
as an exact value. Full evidence and the deployment profile are in
[docs/results-report.md](docs/results-report.md).

## Privacy limitations

- **The weights are public**, by design. If your effect weights are proprietary,
  they would have to be encrypted too, which turns every multiply into a
  ciphertext-ciphertext product and changes the parameter choice.
- **The provider learns the job shape**: the marker count from the number of
  ciphertexts, and the cohort size to within a 32,768 rounding. Not dosages, not
  scores.
- **Honest-but-curious only.** Nothing here proves the provider ran the right
  circuit; a malicious provider could return a wrong answer. Verifiable FHE is a
  separate mechanism.
- **The biobank could compute this in-house.** The weights are public and it
  already holds the genotypes. FHE is what lets the work be offloaded safely;
  the computation itself was always possible in-house.
